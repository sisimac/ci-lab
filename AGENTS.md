# ci-lab — правила работы Codex

Учебный проект: осваиваем CI/CD и Playwright на практике. Подопытный — простое todo-приложение (`app/index.html`), интереса само по себе не представляет. Ценность в пайплайне вокруг него.

Репозиторий: `github.com/sisimac/ci-lab` · Сайт: `sisimac.github.io/ci-lab`
Путь: `~/Developer/ci-lab`

`AGENTS.md` — основной файл проектных правил. Общие личные правила здесь не дублируются. Источники текущего устройства: `package.json`, `package-lock.json`, `playwright.config.ts`, `eslint.config.js`, `.github/workflows/playwright.yml` и `.github/dependabot.yml`. Старые заметки не заменяют проверку этих файлов.

Карта: `app/index.html` — статическое приложение с localStorage, без бэкенда; `tests/todo.spec.ts` — основные E2E и визуальная проверка; `tests/smoke.spec.ts` — смоук. Учебная шпаргалка — `docs/ci-cd-cheatsheet.md`, если она есть локально: папка `docs/` исключена из Git.

## Главное правило: не делать за Александра

**Смысл проекта — научиться, а не получить работающий пайплайн.** Александр не разработчик и выполняет все команды и правки файлов сам, потому что так запоминается.

Отсюда режим работы:

1. Даю **пошаговую инструкцию** — что скопировать, куда вставить, что запустить. Конкретно, без «настройте кэширование».
2. Александр выполняет и пишет «готово».
3. **Я проверяю сам** — читаю файлы, дёргаю GitHub API, сверяю задеплоенное с локальным. Скриншоты и копипаст вывода терминала не нужны и не запрашиваются.

**Не редактировать файлы проекта самому**, даже когда это быстрее. Исключение — если Александр явно поручил соответствующие правки Codex. Такое поручение разрешает выполнить согласованную задачу целиком, но не отключает учебный режим для следующих задач. Чтение файлов, состояния Git и самостоятельная проверка результата разрешены; установку зависимостей и запуск приложения не выполнять только ради знакомства с проектом.

**Не торопить.** Не предлагать следующий шаг, пока текущий не понят. Если объяснение оказалось объёмным — остановиться и убедиться, что оно зашло, а не вываливать следующую порцию.

**Объяснять на его файлах**, а не на абстрактных примерах: «вот эта строка в твоём `playwright.yml`», а не «обычно в workflow пишут».

## Что уже сделано

Пайплайн `lint → test → build → deploy → smoke`:

| Джоба | Что делает |
|---|---|
| `lint` | ESLint |
| `test` | Playwright, три движка, `--grep-invert @smoke` |
| `build` | сборка артефакта |
| `deploy` | GitHub Pages, окружение `production`, отдаёт `outputs.page_url` |
| `smoke` | `needs: deploy`, гоняет `@smoke`-тесты по живому сайту через `BASE_URL` |

Dependabot еженедельно группирует обновления GitHub Actions в `github-actions`, а npm devDependencies — в `dev-dependencies`. Исторически настроены защита ветки и ручной апрув окружения `production`; их актуальные настройки проверять на GitHub при задачах, которые от них зависят. YAML задаёт привязку к окружению, но сам по себе не доказывает наличие обязательного апрува.

`playwright.config.ts`: три браузера, в CI две повторные попытки и один воркер, трейс при ретрае, скриншот при падении. **`retries: process.env.CI ? 2 : 0` разобрано** — см. «Грабли»: ретрай не лечит нестабильность, а снижает вероятность её увидеть. Оставлен намеренно. `webServer` становится `undefined`, когда задана `BASE_URL` — иначе Playwright поднимал бы локальный сервер поверх уже развёрнутого сайта.

## Почему сделано именно так

**Смоук отдельным файлом, а не переиспользованием `todo.spec.ts`.** Три причины: там `goto('/')`, теряющий подпуть; там чистка `localStorage` на каждый тест — лезть в хранилище на проде плохая практика; смоук обязан быть минимальным, а не гонять всю логику приложения.

**Смоук после деплоя только в chromium.** Кросс-браузерность проверяет основная джоба. Локальный `npm test` запускает все найденные тесты, включая смоук, во всех трёх движках; фильтр `--grep-invert @smoke` задан только в основной CI-джобе.

**Адрес через `needs.deploy.outputs.page_url`, а не хардкодом** — чтобы смоук сам ехал за фактическим адресом развёртывания.

**Смоук после деплоя не использовать как обязательную проверку PR.** У `smoke` стоит `needs: deploy`, а деплой выполняется только на push в `main`; на PR смоук пропускается. Проверки, блокирующие слияние, должны действительно проверять PR. Текущий список обязательных проверок устанавливается на GitHub, а не этим файлом.

## Грабли, уже собранные

**`page.goto('/')` теряет подпуть `/ci-lab/`** на GitHub Pages. В смоуке использовать `goto('./')`. В локальных E2E `goto('/')` соответствует серверу в корне; не направлять этот набор на production: он очищает localStorage.

**Локальные браузеры устанавливаются с `PLAYWRIGHT_BROWSERS_PATH=0`** внутрь `node_modules`. Тестовые скрипты и просмотр отчёта в `package.json` уже содержат этот префикс; использовать `npm test` и `npm run test:chromium`. В CI установка и запуск идут напрямую через `npx playwright` без этого префикса, с системным кэшем раннера. Не смешивать два режима. После обновления Playwright проверить наличие браузеров нужной версии.

**Отступы в YAML определяют вложенность.** После изменения workflow проверять его YAML-парсером и сверять граф зависимостей. Ожидаемые ID текущих джоб: `lint, test, build, deploy, smoke`. `js-yaml` не объявлен прямой зависимостью проекта: наличие транзитивного пакета не гарантировано. Не устанавливать утилиты молча ради проверки; выбирать доступный парсер или согласованный способ запуска.

**ID джобы и имя проверки — разные вещи.** При заданном `name:` отображаемое имя проверки может отличаться от ID. Перед переименованием или вводом матрицы сверить фактические имена check runs и правила защиты ветки на GitHub. Не считать, что изменение только ID обязательно меняет имя проверки.

**Рендеринг в Linux и macOS различается** — визуальные регрессионные тесты со снимками падают в CI. Такие тесты в CI пропускать с внятной причиной в `reason`. Снимки в репозитории именно `-darwin`.

**Когда в очереди несколько мержей** — в учебном цикле выбирать деплой последнего нужного прогона. Отмена прогонов и подтверждение production выполняются только в рамках прямого поручения пользователя.

**ESLint разбирает `.ts` обычным JS-парсером.** В `eslint.config.js` для `*.ts` заданы только глобалы Node и отключён `no-undef`, но парсер остался стандартный. Отдельной проверки типов в npm-скриптах нет; отключение `no-undef` само по себе её не добавляет. Пока в тестах нет ни одной чисто-тайпскриптовой конструкции — всё работает. Первое же `const x: string` или `as any` уронит линтер синтаксической ошибкой, а не понятным сообщением. В тестах пишем код, валидный и как JavaScript: вместо `(window as any).render` — `window['render']`.

**После мёржа обновлений от Dependabot — `npm ci` локально.** В CI зависимости ставятся из lock-файла, а локальный `node_modules` остаётся прежним. Так уже расходился ESLint: в lock-файле 10.8.1, в `node_modules` — 9.39.5. Локальная проверка идёт не на том, на чём идёт CI, и «у меня зелёное, а в CI красное» становится вопросом времени.

**Разовое чтение вместо ожидания — главный источник флаков.** `expect(await locator.textContent()).toBe(...)` делает снимок в один момент и не ждёт ничего. `expect(locator).toBeVisible()` опрашивает страницу, пока условие не сойдётся или не выйдет таймаут. Правило: локатор держим внутри `expect`, значение в переменную не вытаскиваем. `waitForTimeout` не использовать вовсе — фиксированная пауза либо мала и даёт флак, либо велика и тормозит прогон.

**Тайминги не переносятся между машинами.** Подобранная локально вероятность падения 50/50 на раннере GitHub превратилась в стабильно зелёный тест: там медленнее обращения к браузеру, шире окно ожидания. Обратный случай тоже проверен — под шестью параллельными воркерами тот же тест падал всегда, потому что таймеры внутри страницы уезжают, когда вкладке не достаётся процессор. Отсюда и «локально зелёное, в CI красное», и строка `workers: process.env.CI ? 1 : undefined`.

**Ретрай повторяет тест вместе с его дефектом.** Он не чинит, а снижает вероятность увидеть красное: при падении в половине случаев две повторные попытки прячут проблему примерно в семи прогонах из восьми. В зелёной джобе факт падения виден только строкой `N flaky` в середине лога и наличием трейса в отчёте (`trace: 'on-first-retry'`).

**Флак нельзя охарактеризовать одним прогоном.** Шесть повторов давали то 5 успехов из 6, то 1 из 6 при одинаковых настройках. Нужна выборка в десятки прогонов или накопленная история — для этого в больших командах и держат дашборды.

**Пуш в ветку без открытого PR не запускает ничего.** Триггеры в workflow — `push` только в `main` и `pull_request` в `main`. Влил PR, продолжил пушить в ту же ветку — проверки молчат, потому что PR закрылся.

**Кнопка «Update branch» меняет ветку на сервере.** Способ обновления может быть merge или rebase. Если локальная копия разошлась с сервером, сначала проверить status и историю, затем выбрать синхронизацию с сохранением работы. Не выполнять pull/rebase/push вслепую.

**Создание PR — задача автора, не ревьюера.** Зелёные проверки разблокируют кнопку слияния, но сами ничего не сливают.

**CD не заканчивается деплоем.** Проверка после развёртывания — часть CD, отсюда и джоба `smoke`.

## Git и границы действий

Перед изменениями проверять текущую ветку, HEAD и `git status`; сохранять чужую и незавершённую работу. После слияния PR в учебном цикле возвращаться к актуальной `main`, прежде чем начинать новую задачу. Сначала проверить локальные изменения и состояние remote; не обновлять checkout и не удалять ветки автоматически ради знакомства или переноса документации.

Новые ветки Codex по умолчанию получают префикс `codex/`. Текущую ветку определять по Git, а не считать её всегда `main`. Commit, tag, push, создание и слияние PR, очистка веток и публикация требуют поручения в текущей задаче; этот файл не даёт на них постоянного разрешения. Учебный план не является поручением начать все пункты.

## Проверка

```
npm run lint          # ESLint
npm test              # Playwright, три движка, локальный сервер поднимется сам
npm run test:chromium # только chromium, быстрее
npm run test:ui       # режим UI: таймлайн прогона, пошаговый разбор, трейсы
npm run report        # HTML-отчёт последнего прогона
npm run app           # поднять приложение отдельно на :5173
```

Для GitHub использовать доступный подключённый инструмент; если его возможностей недостаточно — `gh` или API через `curl`. Наличие утилит и авторизации проверять по месту, не хранить здесь утверждения об их отсутствии. Статус CI проверять самостоятельно, не запрашивать скриншоты. Не читать и не выводить токены.

Обязательные проверки соразмерять изменению. Для правок только Markdown достаточно проверки diff, ссылок и согласованности с конфигурацией; E2E не нужны. Для изменения приложения и тестов — линтер и соответствующий прогон. Для workflow — проверка YAML и логики триггеров, зависимостей и прав. Указывать, что реально проверено и что требует CI или доступа к GitHub.

После изменения `AGENTS.md` проверить его загрузку новым запуском Codex из корня проекта. Текущая сессия не считается автоматически перечитавшей файл. Проверка должна быть только на чтение, без изменения проекта и запуска учебных задач.
